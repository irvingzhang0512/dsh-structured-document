# dsh-structured-document 需求规格说明书 V0.1

## 1. 项目名称

`dsh-structured-document`

中文名称：

**DSH 结构化文档插件**

---

## 2. 项目定位

`dsh-structured-document` 是一个面向 DSH Agent 的、可独立发布的结构化文档操作插件。

插件假设系统已经存在：

```text
当前文件（Current File）
```

本插件不负责：

* 文件选择
* 文件切换
* 文件树展示
* Sidebar 控制

本插件负责：

> 对当前文件进行结构化读取、定位、修改、保存和状态维护，并提供技能（Skill），让大模型能够通过中文自然语言调用这些能力。

项目从 V0.1 开始按照正式发布标准开发：

* 可维护
* 可测试
* 可发布
* 可扩展
* 中文用户友好

---

# 3. 开发与交流语言要求

本项目以中文用户为主要目标用户。

开发过程中要求：

* 与开发 Agent 全程使用中文交流。
* 需求、架构、测试结果、问题分析使用中文。
* README 和 docs 中文优先。
* Skill 以中文自然语言交互为重点。
* 测试用例以中文为主。

代码中的：

* 类名
* 函数名
* Tool 名称
* JSON 字段
* 接口名

使用规范英文。

但所有对外概念必须有明确中文对应关系。

例如：

```text
Document       文档
Node           节点
Role           角色
Properties     属性
Profile        场景模板

Selected Node      当前节点
Last Edited Node   最近修改节点
Last Created Node  最近新增节点
```

---

# 4. 核心链路

```text
中文自然语言
    ↓
DSH Agent
    ↓
结构化文档技能
Structured Document Skill
    ↓
结构化文档工具
Structured Document Tools
    ↓
结构化文档
Structured Document
    ↓
校验并保存
```

用户不需要知道 Tool 名称。

例如：

```text
“在当前节点下面增加一个任务：采集热红外数据。”
```

系统内部转换为：

```text
新增节点（Add Node）

角色：任务 Task
标题：采集热红外数据
父节点：当前节点 Selected Node
```

# 5. 第一阶段应用场景

## 5.1 会议纪要（Meeting Notes）

主要角色：

```text
议题 Topic
讨论 Discussion
问题 Problem
结论 Conclusion
决定 Decision
待办 Action Item
```

主要支持：

* 整理会议结构
* 补充议题
* 调整讨论内容
* 讨论转结论
* 提取决定
* 增加待办
* 为待办增加负责人和截止时间

---

## 5.2 项目管理（Project Management）

主要角色：

```text
目标 Objective
关键结果 Key Result
阶段 / 里程碑 Milestone
任务 Task
问题 Issue
风险 Risk
```

任务常用属性：

```text
负责人 Owner
状态 Status
截止时间 Due Date
进度 Progress
```

---

## 5.3 思路整理（Thinking / Idea Organization）

主要角色：

```text
主题 Topic
问题 Problem
想法 Idea
方案 Solution
疑问 Question
结论 Conclusion
```

主要用于：

* 汇报思路
* 算法方案
* 技术方案
* 日常思考
* 内容梳理

# 6. IR（中间表示）设计

IR（Intermediate Representation，中间表示）采用树形结构。

```text
Document 文档
└─ Node 节点
   ├─ Node
   ├─ Node
   └─ Node
```

---

## 6.1 Document（文档）

```text
id          文档唯一标识
title       文档标题
profile     场景模板
root        根节点
metadata    文档元信息
revision    当前版本
```

---

## 6.2 Node（节点）

```text
id          节点唯一标识
title       标题
content     内容
role        角色
properties  属性
children    子节点
metadata    元信息
```

理解方式：

```text
标题 Title
→ 这部分叫什么

内容 Content
→ 具体说了什么

角色 Role
→ 这部分是什么性质

属性 Properties
→ 负责人、状态等额外信息

子节点 Children
→ 下面还有哪些内容
```

---

# 7. Title（标题）

要求：

* 用户可以随时修改。
* 可以为空。
* 修改标题不能改变 Node ID。
* 节点移动后 Node ID 不变。

---

# 8. Content（内容）

V0.1 支持：

```text
普通文本（Plain Text）
简单 Markdown
```

暂不实现复杂富文本内容块（Block）。

---

# 9. Role（角色）

角色由场景模板（Profile）提供推荐范围。

## 9.1 会议纪要模板

```text
topic           议题
discussion      讨论
problem         问题
conclusion      结论
decision        决定
action_item     待办
```

## 9.2 项目管理模板

```text
objective       目标
key_result      关键结果
milestone       阶段 / 里程碑
task            任务
issue           问题
risk            风险
```

## 9.3 思路整理模板

```text
topic           主题
problem         问题
idea            想法
solution        方案
question        疑问
conclusion      结论
```

---

# 10. Properties（属性）

Properties 根据 Role 使用。

任务（Task）：

```text
owner       负责人
status      状态
due_date    截止时间
progress    进度
```

待办（Action Item）：

```text
owner       负责人
status      状态
due_date    截止时间
```

Properties 为可选字段。

---

# 11. Metadata（元信息）

系统至少维护：

```text
created_at      创建时间
updated_at      修改时间
created_by      创建来源
```

Node ID 必须稳定。

---

# 12. 文档状态（Document State）

至少维护：

```text
Current File
当前文件

Selected Node
当前节点

Last Edited Node
最近修改节点

Last Created Node
最近新增节点

Dirty
是否存在未保存修改

Revision
当前版本
```

---

## 12.1 当前文件（Current File）

V0.1 不负责选择和切换当前文件。

假设外部已经提供 Current File。

必须预留未来集成接口，例如：

```text
set_current_file
设置当前文件

on_current_file_changed
监听当前文件变化
```

该部分标记为：

```text
TODO：当前文件集成
Current File Integration
```

---

## 12.2 当前节点（Selected Node）

例如：

```text
当前节点 = 9月可行性验证
```

用户随后说：

```text
“下面增加一个任务。”
```

默认在当前节点下新增。

---

## 12.3 最近修改节点（Last Edited Node）

支持：

```text
“刚才那个改成风险。”
```

---

## 12.4 最近新增节点（Last Created Node）

支持连续操作：

```text
“增加一个人员检测任务。”

“负责人改成张三。”

“状态改成未开始。”
```

后两句可以默认作用于最近新增节点。

---

# 13. 编辑状态

V0.1 不要求用户先说：

```text
“现在开始修改这个文件。”
```

只要 Current File 存在，就可以直接操作。

未来纯语音连续记录场景再考虑：

```text
开始编辑
结束编辑
```

# 14. 文档工具（Document Tools）

禁止设计一个万能：

```text
document(command)
```

采用职责明确的小 Tool。

# 15. 查看与定位工具

## `get_document`

中文：**获取文档**

获取完整结构化文档。

---

## `get_outline`

中文：**获取大纲**

典型中文：

```text
看看现在的结构。
这个文档有哪些部分？
把大纲给我看一下。
```

---

## `find_node`

中文：**查找节点**

可以根据：

* 标题
* 内容
* 角色
* 属性

查找节点。

如果存在多个候选，不允许随机选择。

---

## `select_node`

中文：**选择节点**

设置当前节点（Selected Node）。

例如：

```text
选中第二个议题。
进入9月验证这一部分。
接下来改这个。
```

---

## `get_selected_node`

中文：**获取当前节点**

返回当前选中的节点。

---

# 16. 基础修改工具

## `add_node`

中文：**新增节点**

支持：

```text

content     内容
role        角色
properties  属性
parent      父节点
position    位置
```

---

## `update_node`

中文：**修改节点**

主要修改：

```text

```

---

## `delete_node`

中文：**删除节点**

例如：


## `move_node`

例如：


## `reorder_node`

中文：**调整顺序**

例如：

```text

```

# 20. 保存机制

默认采用自动保存（Auto Save）。

```text
修改 IR
↓
结构校验
↓
保存
↓
Revision + 1
↓
更新文档状态
```

可以保留：

```text
save_document
保存文档
```

作为调试或特殊场景 Tool。


Skill 不承担真正的文档修改逻辑。

# 23. Skill 操作原则

## 23.1 不确定时先查询

例如：

```text
“把热红外那部分移动到9月下面。”
```

如果没有明确 Node ID：

```text
获取大纲
→ 查找节点
→ 确认目标
→ 移动节点
```

禁止猜测。

## 23.2 多候选必须确认

有多个匹配节点时，必须返回候选或询问用户。

## 23.3 一句话可以包含多个操作

例如：

```text
增加一个人员检测任务，负责人张三，状态未开始。
```

可以一次新增完整节点，也可以组合多个基础 Tool。

## 23.4 用户无需知道 Tool 名

用户使用自然中文即可。

# 24. Tool 返回结果

成功：

```json
{
  "success": true,
  "action": "add_node",
  "node_id": "node_023",
  "revision": 12
}
```

失败：

```json
{
  "success": false,
  "error": "NODE_NOT_FOUND",
  "message": "未找到节点：热红外验证"
}
```

用户可见错误信息使用中文。

---

# 25. 基础错误码

```text
NO_CURRENT_FILE
没有当前文件

NODE_NOT_FOUND
未找到节点

MULTIPLE_NODES_FOUND
找到多个候选节点

INVALID_ROLE
角色不合法

INVALID_PROPERTY
属性不合法

INVALID_OPERATION
操作不合法

SAVE_FAILED
保存失败

VALIDATION_FAILED
结构校验失败
```

---

# 26. 结构校验

所有修改必须经过结构校验（Schema Validation）。

至少保证：

* Node ID 唯一。
* Children 结构合法。
* 不产生循环结构。
* Role 符合当前 Profile。
* Properties 类型合法。
* 修改失败不留下半完成状态。

# 36. 多轮中文交互测试

除单条命令外，必须测试连续多轮上下文。

例如：

```text
用户：选中9月计划。

用户：下面增加一个任务，完成热红外验证。

用户：负责人张三。

用户：状态先设成未开始。

用户：把它移动到第一项。

用户：不对，撤销。
```

系统必须正确理解：

```text
“它”
“负责人”
“状态”
```

都指向前面刚新增的节点。

---

# 37. 歧义测试

必须测试中文自然语言中的歧义。

例如文档中存在两个：

```text
验证计划
```

用户说：

```text
选中验证计划。
```

系统不得随机选择。

应返回：

```text
找到多个“验证计划”，请确认：
1. 9月 / 验证计划
2. 10月 / 验证计划
```

---

# 38. 发布前真实体验测试

正式发布前至少使用三份真实规模文档进行人工测试：

```text
1份会议纪要
1份项目管理文档
1份思路整理文档
```

每份文档至少完成：

* 10 次以上连续自然语言操作
* 新增
* 修改
* 删除
* 移动
* 排序
* 修改角色
* 修改属性
* 撤销

重点检查：

> 用户是否可以只使用正常中文完成修改，而不需要知道内部 Tool、Node ID 或 IR 格式。

# 39. 开发过程要求

开发 Agent 必须：

1. 开发前完整阅读本需求。
2. 全程使用中文与用户交流。
3. 检查实际 DSH Plugin / Tool / Skill API。
4. 不凭空假设不存在的接口。
5. 先开发 IR 和底层操作，再开发 Skill。
6. 每阶段完成后用中文说明：

   * 已完成内容
   * 测试结果
   * 存在的问题
   * 与需求的差异
7. 不得擅自扩大范围。
8. 实际架构与需求冲突时，用中文说明设计选择。
9. 所有场景测试必须真正执行，而不是只编写测试文档。

# 42. 一句话定义

`dsh-structured-document`：

> 为 DSH 提供统一的结构化文档模型、文档状态、节点操作 Tool 和中文自然语言 Skill，使 Agent 能够通过正常中文稳定地读取、定位、修改和重组会议纪要、项目管理、思路整理等结构化文档，并作为可独立发布的通用插件使用。
